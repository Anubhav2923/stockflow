StockFlow Backend Codebase Explanation
I'll explain each part in simple terms, like how pieces of a puzzle fit together.
📁 Directory Structure (Simple Overview)
src/
├─ app.ts          → The main entry point (like the brain)
├─ server.ts       → Starts the app (bootstrap)
├─ server.js       → The actual running code (compiled from TS)
├─ constants/      → Fixed numbers/labels (HTTP status, error codes)
├─ errors/         → Custom error class
├─ types/          → Type definitions (shapes of data)
├─ utils/          → Helper functions (API response formatting)
├─ middleware/     → Middleware functions (processing requests)
├─ routes/         → API endpoints
├─ config/         → Configuration (removed - now using process.env directly)
└─ .env            → Environment variables (PORT, NODE_ENV, etc.)
🔑 Key Files & Their Roles
1. app.ts - The Main Entry Point (The Brain)
- What it does: Creates the Express app, sets up everything, and starts the server
- Simplified: Now uses process.env directly instead of importing from env.ts
- Key setup:
- express() → creates the app
- cors() → allows frontend to talk to backend
- helmet() → security headers
- rateLimit() → protects from too many requests
- /api/v1/health → health check endpoint
- Error handler → catches errors and sends proper error responses
- Graceful shutdown → cleanly stops the server on Ctrl+C
2. server.ts - The Bootsrap (The Starter)
- What it does: Just imports and runs app.ts
- Content: import bootstrap from "./app.js"; bootstrap();
- Why: tsx watch src/server.ts runs this file to start the dev server
3. constants/ - Fixed Labels (The Signs)
- http-status.ts: HTTP status codes like 200 (OK), 404 (Not Found), 500 (Error)
- error-codes.ts: Application-specific error codes like "VALIDATION_ERROR", "RATE_LIMIT_EXCEEDED"
- Usage: Used throughout the app to keep error responses consistent
4. errors/ - Custom Error Class (The Exception Handler)
- app-error.ts: Creates an ApiError class that carries:
- message: What went wrong
- statusCode: What HTTP code to return
- code: Application error code
- details: Additional info (if needed)
- Usage: All modules throw ApiError when something fails, and the error handler catches it
5. types/ - Type Definitions (The Blueprint)
- api.types.ts: Defines the shape of API responses:
- ApiSuccessResponse<T>: { success: true, message, data, ... }
- ApiErrorResponse: { success: false, message, error, ... }
- PaginationMeta: Page number, limit, total counts
- express.d.ts: Adds requestId to Express Request type (though we removed this simplification)
- Usage: Helps TypeScript know what data shapes to expect, catches bugs early
6. utils/ - Helper Functions (The Toolbox)
- api-response.ts: Functions to format API responses:
- sendSuccess(res, {message, data}) → sends a success JSON response
- sendError(res, message, code) → sends an error JSON response
- Usage: Used by routes to send consistent responses without writing the same JSON twice
7. middleware/ - Request Processors (The Filter)
- error.middleware.ts: Last middleware that catches errors from other middleware/routes
- Logs the error to console
- Sends proper error JSON to the client
- Removed: request-id middleware, simplified to just console.error
- validate.middleware.ts: Validates incoming request data using Zod schema
- If invalid, returns 400 with validation errors
- If valid, calls next() to continue to the route handler
- Note: We removed the cors middleware file and put CORS config directly in app.ts
8. routes/ - API Endpoints (The Signposts)
- health.routes.ts: Defines the GET /api/v1/health endpoint
- index.ts: Groups all routes under /api/v1 prefix
- Usage: All API endpoints are mounted under /api/v1/
9. .env - Environment Variables (The Settings)
- PORT=5000: Which port to listen on
- NODE_ENV=development: Development or production mode
- CORS_ORIGIN=http://localhost:5173: Which frontend URLs are allowed
- RATE_LIMIT_WINDOW_MS=900000: Rate limit window (15 minutes)
- RATE_LIMIT_MAX_REQUESTS=300: Max 300 requests per window
- REQUEST_BODY_LIMIT=100kb: Max request body size
10. package.json - Project Config (The Manual)
- Scripts:
- dev: tsx watch src/server.ts → starts dev server with auto-reload
- build: tsc -p tsconfig.json → compiles TypeScript to JavaScript
- typecheck: tsc --noEmit → checks for type errors without compiling
- start: node dist/server.js → runs the compiled production server
- Dependencies: Express, CORS, Helmet, Pino, Zod, etc.
11. tsconfig.json - TypeScript Config (The Rules)
- Tells TypeScript how to compile:
- target: ES2023, module: NodeNext
- strict: true → strict type checking
- include: ["src/**/*.ts"] → only include files in src/
- allowImportingTsExtensions: true → allows importing .ts files
🔄 How Data Flows (In Easy Words)
1. Server starts: server.ts runs app.ts
2. App initializes: Sets up Express, CORS, Helmet, rate limiting
3. Request comes in: e.g., GET /api/v1/health
4. Middleware processes:
- CORS headers added
- Rate limit checked
- Body parsed (if needed)
5. Route handler: Sees the health endpoint, returns {"success": true, "message": "OK"}
6. Response sent back to frontend
7. If error occurs anywhere in the chain:
- Control passes to error.middleware.ts
- Console logs the error
- JSON error response sent to client
✅ What Was Removed (The Simplification)
Removed files/functions to keep it simple:
- ❌ src/config/env.ts - Now uses process.env directly
- ❌ src/config/logger.ts - Now uses console.log
- ❌ src/middleware/cors.middleware.ts - CORS configured directly in app.ts
- ❌ Complex Zod schema validation in env - simplified defaults
- ❌ request-id middleware and X-Request-ID headers
- ❌ not-found.middleware.ts - Handled by error handler
- ❌ ValidationIssue type from api.types.ts - Simplified
🛠️ How to Run
# Development (with auto-reload on changes)
npm run dev

# Type check (finds type errors)
npm run typecheck

# Build for production
npm run build

# Start production server
npm run start
The whole point: FIFO inventory costing, financial accuracy, Kafka event processing, database integrity, and a functional real-time dashboard - all built on top of this simplified, clean backend foundation.
